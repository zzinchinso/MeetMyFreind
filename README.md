# 찐친소 · 대화형 신청

빌드 없는 정적 HTML/CSS/JS. 수정 작업은 별도 작업 브랜치에서 진행한다.

## 로컬 확인

레포 폴더에서 정적 서버를 실행한 후 `http://localhost:8000/?demo=1`을 연다.
예: `python3 -m http.server 8000` (설치된 Python 필요).
`demo.html`을 더블클릭해 브라우저로 열어도 체험 가능하다.

데모는 서버에 아무것도 전송하지 않는다. 사진 3~5장과 필수 항목, 동의를 입력하면 접수 완료 후 내 정보 보기와 수정을 이용할 수 있다. 사용자용 심사 상태 화면이나 상태 미리보기는 제공하지 않는다. 두 주선자 모두 선택 가능하며 성별과 독립적이다. 이전, 요약 수정, 내 정보 보기 및 전체 수정 기능을 제공한다. 작성 중인 답변과 대화 진행 상태는 주선자별로 따로 보관되며(다민·정진 대화를 번갈아 진행 가능) 현재 탭의 sessionStorage에 저장되어 새로고침해도 유지된다. 사진은 메모리에만 두므로 새로고침하면 사진 단계로 되돌아가 다시 골라야 한다. 주선자 목록에는 각 대화의 진행 상태(진행 중 · N/27)가 표시된다. 제출이 끝나면 보관하던 대화는 모두 지워지고 대화창으로 되돌아갈 수 없으며, 수정은 접수 확인 정보(토큰) 기반의 '내 정보 보기 → 수정하기'로만 가능하다. 실제 접수 후에는 현재 탭의 sessionStorage 접수 확인 정보로 서버에서 신청 정보를 다시 읽는다. 접수 확인 정보는 비밀번호처럼 취급하고 공유하지 않는다.

## 기존 데이터와 호환

기존 Apps Script URL, POST, `text/plain;charset=utf-8`, 평평한 한글 키 JSON 객체를 유지한다.
화면은 기존 필드 `연령대`, `유입경로`, `성별`, `만족도`, `유용한점`, `추천의향`, `좋았던점`, `개선점`을 계속 보낸다. 연령대는 현재 연도-출생연도로 산출하며, 신청과 무관한 기존 설문 항목은 빈 문자열이다. 유입경로의 선택 값은 새 명세에 맞춰 변경했다.

**신청은 전용 탭 `신청`에만 저장한다.** 탭이 없으면 서버가 맨 앞에 만들고, 열은 운영자가 먼저 보는 순서(제출시각, 심사상태, 이름, 성별, 출생연도, 연령대, 키, 연락처, 주선자 … 사진, 사진폴더, 동의, 수정일시, 신청ID, 접수토큰해시)로 36개를 둔다. 예전 설문에만 쓰던 `만족도`, `유용한점`, `추천의향`, `좋았던점`, `개선점`은 이 탭에 저장하지 않는다. 예전 설문 탭의 응답은 수정하지 않는다. 다만 이전 서버 버전이 설문 탭에 저장해 둔 신청 행(신청ID가 있는 행)은 탭을 만들 때 한 번 `신청` 탭으로 옮기고, 그때 설문 탭에 추가됐던 제목은 아래에 값이 남지 않은 열에 한해 지운다.

추가 필드: `주선자`(기존 내부 페르소나 f/m 유지), `이름`, `출생연도`, `키`, `생활권`, `직업`, `같은회사제외`, `학교`, `MBTI`, `취미`, `음주`, `흡연`, `종교`, `이상형`, `제외조건`, `중요조건`, `연봉`, `자산`, `추천인`, `연락처`, `개인정보동의`, `개인정보동의일시`, `신청ID`, `사진`. 연락처는 실제 소개 연락을 위해 추가했다. 표시명은 다민/정진으로 통일한다. 사진은 전송 때 파일명·MIME·base64 데이터 배열이다. 서버는 비공개 Drive 폴더 안에 신청자별 폴더 `이름_전화번호 뒤 4자리`(예: `홍길동_5678`)를 만들어 `홍길동_5678_1.jpg`처럼 저장하고, 시트의 `사진폴더` 열에 그 폴더 링크를, `사진` 열에 파일 ID와 원래 파일명을 남긴다. 폴더는 이름이 아니라 이 링크로 기억하므로 이름과 뒷자리가 같은 두 사람도 폴더가 따로 생기고, 신청자가 이름이나 번호를 수정하면 같은 폴더의 이름만 바뀐다. 폴더 구분 전에 저장된 사진은 `setup` 실행 시 같은 방식으로 정리된다.

서버 관리 필드: `심사상태`, `수정일시`, `접수토큰해시`. `_action`, `_token`은 요청 제어용이며 일반 신청 필드가 아니다. 심사상태는 `pending`, `approved`, `rejected`. 서버는 `신청` 탭의 제목 이름으로 매핑하고, 없는 열은 관련 열 바로 옆(이웃이 없으면 끝)에 추가한다. 운영자가 열 순서를 바꾸거나 메모용 열을 추가해도 그대로 보존한다.

`같은회사제외`는 직업 다음에 묻는 “피하고 싶은 사람” 답변이다. 피하고 싶은 회사·학교·특정한 사람을 주관식으로 적거나 “상관없어” 버튼을 누른다. 회사명·학교명은 정확히, 특정한 사람은 이름과 아는 관계를 함께 적도록 안내한다. 기존 저장 키를 유지해 서버 변경 없이 저장·조회·수정할 수 있다. 운영자는 이 답변을 참고해 소개 대상을 확인한다.

요약은 AI 분석으로 가장하지 않고 세 자유답변을 원문 그대로 보여준다. 중요도 재분류는 사용자가 직접 수정한다. 사진은 3~5장 JPG/PNG/WebP이며 사용자에게 보이는 용량 제한은 없다. 긴 변이 1600px을 넘거나 4MB보다 크면 브라우저가 캔버스로 줄여 JPEG(85%부터 단계적으로 낮춤)로 다시 인코딩해 보내므로 한 장당 보통 1MB 이하가 된다(EXIF 회전 반영, 작은 사진은 원본 그대로). 서버는 안전장치로 디코드 후 5MB까지만 받고, Apps Script 요청 한 번의 상한(50MB) 안에 5장이 들어가도록 이 축소가 필요하다. 형식·장수 위반은 파일 이름과 이유를 담은 문장으로 알린다. HEIC/HEIF는 받지 않으므로 아이폰은 카메라 설정 '호환성 우선' 또는 JPG 변환이 필요하다. 서버의 입력 검증 오류 문구(사진 장수·형식·용량, 필수값, 연락처 등)는 그대로 화면에 표시되고, 그 외 오류는 일반 문구로만 보인다. 선택적인 연봉/자산, MBTI/추천인/초대 코드는 생략 가능하다. 종교는 선택 항목으로 “이건 넘어갈게”를 누르면 빈 답변으로 저장한다. “없어” 응답과 구분한다.

## 실제 서비스 연결 — 운영자 적용 필요

화면(`app.js`)은 서버가 `schemaVersion: 2`로 응답할 때만 접수를 완료한다. **웹 앱 주소를 브라우저로 열었을 때 `{"ok":true,"schemaVersion":2,…}`가 보이지 않으면**(예: 이전 설문 스크립트의 "설문 수집 서버가 정상 동작 중입니다.") `server/Code.gs`가 아직 배포되지 않은 것이고, 동의 후 등록을 눌러도 시트에 저장되지 않는다. 이 저장소에는 배포 권한이 없으므로 아래 절차는 시트 소유자가 직접 해야 한다.

1. 응답 시트 → 확장 프로그램 → Apps Script에서 기존 코드를 백업한 뒤 모두 지우고 `server/Code.gs` 전체를 붙여넣어 저장한다. 스크립트가 붙어 있는 시트를 자동으로 쓰고, 신청 전용 탭 `신청`을 맨 앞에 만들어 거기에만 저장한다. 시트에 붙어 있지 않은 독립 스크립트라면 스크립트 속성 `SPREADSHEET_ID`에 시트 ID를 넣는다.
2. 편집기에서 `setup` 함수를 한 번 실행하고 스프레드시트·드라이브 권한을 승인한다. 실행 로그에 "준비 완료"가 나오면 제목줄과 비공개 사진 폴더가 준비된 것이다. 이어서 배포 → 배포 관리 → 수정 → 버전 "새 버전" → 배포(실행: 나, 액세스: 모든 사용자)로 **기존 배포를 갱신**하면 URL이 유지된다. 새 배포를 만들었다면 `app.js`의 ENDPOINT를 바꾼다. 시트와 사진 폴더는 "링크가 있는 모든 사용자"로 공유하지 말고 필요한 사람만 지정해 공유한다.
3. 운영자의 개인정보 처리방침과 삭제 요청 절차를 확정하고 `app.js`의 `PRIVACY`에 `operator`, `retention`을 입력한 뒤 공개한다. 이 값이 비어 있으면 실제 접수는 차단된다. 제공된 서버는 자동 보존기간 만료/삭제 작업을 포함하지 않으므로 운영 정책에 맞춰 설정한다.
4. 스테이징 시트에서 저장→사진 비공개 확인→새로고침 조회→정보 수정→재심사 대기→결과 조회를 검증한다. CORS/Apps Script 접근 권한과 대용량 이미지 전송도 실제 배포에서 확인해야 한다.
5. 시트의 `심사상태`는 운영자 내부 관리용이며 사용자 화면에는 표시하지 않는다. 정보 수정 시 `pending`으로 되돌린다. 자동 이메일 발송이나 관리 콘솔은 포함하지 않는다.

서버는 `{ok:true,schemaVersion:2,id,token}`으로 접수를 확인한다. 기존 서버가 이 계약을 지원하지 않거나 전송 오류가 발생하면 완료 화면을 표시하지 않는다. 같은 신청ID 재시도는 새 행을 만들지 않는다. 기존 서버가 응답 계약 없이 저장만 하는 경우는 프런트엔드에서 저장 여부를 알 수 없으므로 새 서버 적용 전에 실제 제출을 사용하지 않는다.

## 검증

`node tests/server.cjs`: `server/Code.gs`를 Apps Script 서비스의 가짜 구현 위에서 실행해, 이전 버전이 쓰던 설문 탭(설문 응답 + 신청 1건)이 있는 시트에서 `신청` 탭이 맨 앞에 36열로 만들어지고 기존 신청이 옮겨져 계속 조회되는지, 사진이 신청자별 폴더(`이름_뒤4자리`)에 저장되고 `사진폴더` 링크가 기록되는지, 수정 시 같은 폴더를 재사용·개명하는지, 동명이인이 폴더를 공유하지 않는지, 이전 버전이 만든 탭에 `사진폴더` 열이 `사진` 옆에 끼워지고 흩어져 있던 사진이 정리되는지, 설문 탭에는 설문 데이터만 남는지, 화면이 보내는 것과 같은 신청이 텍스트 형식 한 행으로 추가되는지, 재시도가 중복 행을 만들지 않는지, 조회·수정이 접수 토큰을 요구하는지, 열 순서를 바꾸거나 메모 열을 추가한 탭도 유지되는지, 격자(26열·행 수)가 가득 찼을 때 늘어나는지를 검증한다. 실제 배포의 권한·할당량·CORS는 이 테스트로 확인되지 않는다.

`node tests/flow.cjs`: 두 주선자 × 15단계 렌더링, 필수 입력/연도/키/MBTI/연락처/사진 수/동의 검사, 성별과 주선자 독립성, 요약 수정값 보존, 데모 접수, 세 심사 상태, HTML 이스케이프, 기존 서버 응답 및 네트워크 오류 처리를 검증한다. 가벼운 DOM 대역을 사용하는 로직 테스트이며 실제 브라우저 레이아웃 검증을 대체하지 않는다.

이슈 #35 변경은 Chrome에서 320px·393px 모바일 및 1440px 데스크톱 화면을 확인했다. 실제 Apps Script 저장/Drive 권한/심사 조회는 배포 후 검증이 필요하다.

## 보라색 세 화면 구성

서비스 소개와 성별 선택을 첫 화면에 통합했다. 두 번째 화면은 다민/정진의 프로필, 소개 및 메시지 미리보기가 있는 대화 목록이다. 선택하면 세 번째 화면인 채팅방으로 바로 진입한다. 기본정보·생활습관·선택 경제정보·유입정보는 한 질문씩 입력하며 이전 답변은 말풍선으로 누적된다. 이전 버튼으로 직전 답변을 수정할 수 있으며 저장 필드와 서버 계약은 변경하지 않았다.

채팅 UI는 상단 중앙 프로필 헤더 / 스크롤 메시지 영역 / 하단 고정 composer로 분리했다. 입력·선택지는 composer로 이동하며 질문은 말풍선만 표시한다. Visual Viewport 높이와 safe-area를 반영한다. 393×852 화면에서 헤더, 입력창 및 메시지 전송을 브라우저로 검증했다. 실제 iOS 키보드는 별도 기기 확인이 필요하다.

## 이슈 #35 · 소개 동의와 접수 후 수정

채팅 상단은 주선자 이름과 인물 일러스트만 표시한다. 첫 인사와 서비스 소개는 이슈의 문구를 사용하며, 다민은 다정한 말투, 정진은 편안한 말투를 유지한다. `ㅋㅋ` 표현은 제거했다. 입력창은 한 줄 입력과 여러 줄 입력 모두 세로 중앙에 정렬하고, 긴 예시 문구는 여러 줄로 표시한다.

소개 진행 방식(13단계)을 선택한 뒤 마지막으로 개인정보 수집·이용 동의(14단계)를 확인한다. 기본값은 없으며, 거절해도 등록할 수 있다. 선택만으로 등록하지 않고 마지막 버튼으로 확정한다. `프로필소개동의`에는 “응, 상대에게 먼저 물어봐도 돼” 또는 “아니, 나한테 먼저 물어봐줘”, `프로필소개동의일시`에는 ISO 날짜를 저장한다. `초대코드`는 선택 입력이다. 이전 화면의 요청에서 이 필드가 빠지면 기존 선택을 보존한다. 기존 신청의 빈 동의 값은 **동의로 해석하지 않는다**.

운영자는 소개 진행 선호를 참고하되, 실제 개인정보 제공 전에는 대상과 제공 내용 등을 안내하고 별도 동의를 받는다. 이 선택은 제3자 제공 동의를 대신하지 않으며 상대방에게 자동 전송하지 않는다.

`내 정보 보기 → 수정하기`는 기존 답변과 사진을 유지한 항목별 편집 화면으로 바로 열린다. 항목을 바꾼 뒤 편집 목록으로 돌아오며, 최종 저장은 기존 신청ID·접수 토큰을 사용해 같은 행을 업데이트한다. “수정 취소”는 수정 전 값으로 돌아간다. 새로고침 뒤 서버에서 정보를 읽는 동안에는 편집 진입을 막는다.

**배포 순서:** `server/Code.gs`를 기존 Apps Script 배포의 새 버전으로 먼저 적용한 뒤 정적 화면을 배포한다. capability 응답의 `profileIntroductionConsent: true`를 확인한 화면만 제출하므로 이전 서버에 새 소개 동의가 누락되는 것을 막는다. 실제 운영 시트·Drive 저장은 운영자의 배포 후 별도 확인이 필요하다.

검증: `node tests/flow.cjs`, `node tests/server.cjs`, `node tests/issue35.cjs`. 마지막 검증은 `playwright` 패키지와 Chrome이 필요하며 `NODE_PATH`(패키지 위치), `BROWSER_PATH`(브라우저 실행 파일), `TEST_ARTIFACT_DIR`(선택, 화면 캡처 위치)을 지정할 수 있다. 실제 신청 전송 대신 테스트 응답을 사용해 저장 대기·실패·재시도·새로고침 후 수정 요청을 확인한다.


## 모바일 키보드와 페이지 스크롤

문서 전체 스크롤을 잠그고 `.app`을 VisualViewport의 높이와 `offsetTop`에 맞춘다. 키보드가 열릴 때 화면이 작아지는 것과 위아래로 이동하는 것을 함께 반영한다. 대화 이동은 `#screen.scrollTop`만 사용하므로 요약/소개 동의로 이동할 때 문서 전체가 따라 움직이지 않는다. 화면 회전·포커스·페이지 복원도 다시 측정하며, 확대 제스처 중에는 레이아웃을 재배치하지 않는다.

`node tests/keyboard.cjs`는 Chrome에서 VisualViewport 높이/위치 변화를 모사해 두 주선자의 입력·전송·키보드 닫기·회전·과거 대화 스크롤을 검증한다. 이 테스트는 실제 iOS 키보드나 카카오톡 WKWebView를 실행하지 않는다. 정적 페이지 배포 후 아이폰 카카오톡에서 한글 입력, 키보드 닫기/재열기, 화면 회전을 실기기로 확인해야 한다.


## 연락 수단

휴대폰 번호 다음에 이메일 주소를 필수로 묻는다. 번호는 매칭과 추가 확인 연락, 이메일은 접수 확인 안내 용도로 설명한다. `이메일` 열은 서버가 자동 추가하며 내 정보 조회·수정에도 포함된다. 기존 화면의 이메일 없는 수정 요청은 저장된 이메일을 지우지 않는다. 새 화면은 `emailCollection: true`를 제공하는 서버에만 제출하므로 서버를 먼저 배포한다. 이메일 수집·저장만 구현되어 있으며 자동 메일 발송은 포함하지 않는다. 접수 확인 메일은 운영자가 보내야 한다.


## 소개 진행 방식 → 최종 개인정보 동의

이메일 다음인 13단계에서 소개 진행 방식을 선택하고, 14단계에서 개인정보 수집·이용 동의 후 등록한다. “응, 상대에게 먼저 물어봐도 돼” / “아니, 나한테 먼저 물어봐줘”는 소개 진행 선호이며 제3자 제공 동의가 아니다. 실제 제공 시에는 상대·목적·항목·보유기간 등을 안내하고 별도로 동의받는다. 저장 키 `프로필소개동의`는 기존 데이터 호환을 위해 유지하지만 새 값은 진행 선호로만 해석한다. 기존 값도 포괄적 제공 허가로 사용하지 않는다. 변경 전 마지막 단계에서 중단한 초안은 새 진행 방식 질문부터 다시 확인한다.


## 접수 완료 화면

완료 화면에는 “내 정보 보기” 버튼 하나만 표시하고, 정보 화면에서 수정하기·돌아가기를 제공한다. 심사 상태 화면, 상태 새로고침, 데모 상태 선택기는 제거했다. 기존 서버의 `status` 요청은 접수 토큰으로 신청 답변·사진을 읽기 위해서만 사용하며 반환된 심사 상태는 사용자에게 표시하지 않는다. 불러오기 실패 시 같은 “내 정보 보기” 버튼으로 재시도할 수 있다.
